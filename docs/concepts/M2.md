# M2 concepts: a transformer in plain Rust

What M2 introduced, how each idea works, and where it lives in the code. Read alongside
`train/src/glasswing_train/model.py`: the Rust mirrors it step by step.

## 1. Reading safetensors by hand

```text
[8 bytes: header length N, little-endian u64][N bytes: JSON header][raw tensor bytes]
```

The header maps each tensor name to `{"dtype": "F32", "shape": [64, 64], "data_offsets": [start, end]}`,
plus `"__metadata__"` (our model config lives there). Loading a tensor is: slice
`data[start..end]`, take 4 bytes at a time, `f32::from_le_bytes`. "Little-endian" means the least
significant byte comes first; x86, ARM and WebAssembly are all little-endian, but we say it explicitly
so the code is correct everywhere.

The reader **validates before trusting**: the header length must fit the file, each tensor's offsets
must lie inside the data, and `end - start` must equal `numel × 4`. A truncated or hostile file fails
with a message instead of reading out of bounds. Then the model loader checks every weight's shape
against the config. Tests for the bad cases are in the same file.

**Code:** `crates/engine/src/safetensors.rs`. `serde_json` parses the JSON header; that's the only
dependency, and it's for JSON, not math.

## 2. Row-major layout and the `[out, in]` weight convention

A tensor is a flat `Vec<f32>` plus a shape. In a `[T, D]` matrix, element `(t, d)` is at `t * D + d`:
each row is contiguous. Activations are `[T, ...]`, one row per token.

PyTorch's `nn.Linear` stores its weight as `[out, in]`. Computing `y = x · Wᵀ` therefore means:
**each output value is the dot product of one input row with one weight row**, and both rows are
contiguous in memory. The CPU reads both arrays front to back, which is what caches and prefetchers
are built for, and the compiler can vectorise the loop. That is `ops::linear`.

Q/K/V come out as `[T, H·Hd]`: per token, head 0's 64 numbers, then head 1's, and so on. The reference
traces them per head (`[H, T, Hd]`), so `heads_first` reorders them only when tracing is on.

## 3. The operations

Everything the model does is six operations in `crates/engine/src/ops.rs`:

| op | what it does |
|---|---|
| `linear` | matrix × weightᵀ, one dot product per output |
| `rmsnorm` | per row: `x / sqrt(mean(x²) + eps) * weight` |
| `apply_rope` | per head, rotate pairs `(i, i+32)` by the angle for that position and pair |
| `softmax` | `exp(x - max) / sum` |
| `silu` | `x / (1 + e^-x)`, the gate's nonlinearity |
| add | the residual connection, `x += f(x)` |

`model.rs` composes them: embed → 8 × (norm → attention → add → norm → SwiGLU MLP → add) → norm →
logits.

**Attention, the loop version** (`model.rs::attention`): for each query head h, and each position t,
score positions `s = 0..=t` as `q_t · k_s / √Hd`, softmax those scores, and add up `weight_s × v_s`.
Two things are visible here that PyTorch hides:

- **The causal mask is the loop bound.** PyTorch computes the full T×T score matrix and overwrites the
  future with −∞. We never compute those scores at all. Same result, half the work.
- **GQA is integer division.** Query head h reads key/value head `h / group`. In the fixture model,
  4 query heads share 2 kv heads: heads 0,1 use kv 0; heads 2,3 use kv 1. That matches PyTorch's
  `repeat_interleave`.

## 4. Numerically stable softmax

`softmax(x)ᵢ = e^xᵢ / Σⱼ e^xⱼ`. In f32, `e^89` is already infinity, and `∞ / ∞` is NaN. Subtracting
the maximum first gives `e^(xᵢ − max) / Σ e^(xⱼ − max)`: the factor `e^−max` cancels between top and
bottom, so the result is identical, but now every exponent is ≤ 0 and the largest term is exactly 1.
`ops::tests::softmax_survives_huge_logits` feeds it 1000 to prove it.

## 5. Parity testing

`crates/engine/tests/parity.rs` loads the M1 fixtures, runs the three prompts with a `Trace`, and
compares **every traced tensor in computation order** (78 of them) against PyTorch, with
`|rust − pytorch| ≤ 1e-4 + 1e-4·|pytorch|`. It reports the first divergence, because a bug makes
everything after it wrong too. It also checks that the Rust trace covers every tensor the fixture has,
and that no value is NaN or infinite.

The tokenizer has its own parity test against `tokenizer_cases.json` (unicode, emoji, Cyrillic and
Arabic, multiple spaces, `\r\n`, special tokens, an unknown long word). The Rust pre-tokenizer is a
hand-written byte scanner rather than a regex, because Rust's `regex` crate doesn't support the
lookahead `(?!\S)`. The comment in `tokenizer.rs::pretokenize` explains how the scanner reproduces it.

Result: all 78 tensors and all 11 tokenizer cases match on the first run, on Windows and in CI.

real weight, just in the wrong place.

Prediction: layer 0 still matches; the first divergence is `layers.1.q`.

Result: `first divergence at p0.layers.1.q [4, 19, 16]: index 285: rust -3.1186633 vs pytorch 2.2356944`.
Shape checks can't catch layout bugs on square matrices; only comparing values can. The stage-by-stage
