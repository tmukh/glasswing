# M1 concepts: tokenizer, transformer, golden fixtures

What M1 introduced, how each idea works, and where it lives in the code.

## 1. Tokenization and byte-pair encoding (BPE)

A model reads integers, not text. One id per byte (256 ids) works but wastes the model on spelling:
"Once upon a time" would be 16 steps. **BPE** starts from the 256 bytes and repeatedly finds the most
frequent adjacent pair in the training text, makes it a new token, and replaces it everywhere. It is
dictionary compression learned from the data. Our first merges were ` t`, `he`, ` a`, ` s`, ` w`, `nd`,
` the`; the last ones were whole words like ` television` and ` igloo`.

**Pre-tokenization** splits text into chunks first (a word with its leading space, a digit run, a
punctuation run, whitespace). Merges never cross chunk boundaries, so `dog.` stays `dog` + `.`, and the
token for ` dog` is the same wherever the word appears. The leading space belongs to the word: ` the`
and `The` are different tokens, which is why ids for "Once upon a time" are `Once`, ` upon`, ` a`, ` time`.

**Vocabulary size is a trade-off.** Every token costs a row in the embedding table (384 numbers) and an
output in the last layer. GPT-2's 50k vocabulary would be 19M parameters at our width, more than the
whole model. TinyStories uses a few thousand distinct words, so 4096 is enough.

Measured on the validation set (unseen stories): **3.93 bytes per token**, and **97.4%** of chunks are
a single token. An astrophysics sentence falls apart (` a`+`st`+`ron`+`om`+`er`): a tokenizer is only
efficient on text like its training data.

**Code:** `train/src/glasswing_train/tokenizer.py`
- `PRETOKENIZE`: the chunking regex, on bytes so Rust can reproduce it exactly.
- `train_bpe`: counts each *distinct* chunk once with its frequency (64M chunks in the sample, but only
  32k distinct ones), keeps pair counts in a heap, and on each merge updates only the chunks that
  contain the pair. Training took 1 second; counting the 256 MB sample took 14.
- `Tokenizer._encode_chunk`: repeatedly merges the adjacent pair that was learned *earliest*. That
  replays training on any chunk, which is why encoding needs only the merge list, not the counts.
- Ids: 0–255 bytes, 256–4094 merges in learned order, 4095 `<|endoftext|>` (story boundary).

## 2. The transformer and the residual stream

Each token position carries one vector of 384 numbers, the **residual stream**. The embedding table
gives the starting vector; then 8 blocks each *read* a normalised copy of the stream, compute
something, and *add* it back (`x = x + f(norm(x))`). Nothing overwrites the stream, so every layer can
see what earlier layers wrote, and gradients flow straight back through the additions during training.

Each block has two stages:

**Attention moves information between positions.** For every position, three projections of the
stream: a **query** ("what am I looking for?"), a **key** ("what do I offer?") and a **value** ("what
do I hand over if chosen?"). Score = query · key / √64, for every earlier position. **Softmax** turns
the scores into weights that sum to 1, and the output is the weighted average of the values. Six
**heads** do this in parallel with their own projections, so one head can track "who is the subject"
while another tracks "what was the previous word". `o_proj` mixes the heads back into the stream.

The **causal mask** sets scores for later positions to −∞ before the softmax (weight 0). Training
predicts the next token at every position at once; without the mask, position t could just read token
t+1. See the break-it lab below.

**The MLP works on each position alone:** 384 → 1024 → 384. The 1024 intermediate values are the
**neurons**. Attention gathers context; the MLP is where most of the "knowledge" is stored.

At the end, a final RMSNorm and a projection onto the vocabulary give **logits** (4096 scores); softmax
gives next-token probabilities. With **tied embeddings** that projection reuses the embedding table,
so a token's logit is the dot product of the final stream with that token's embedding.

## 3. The Llama parts

- **RMSNorm:** divide the vector by its root-mean-square, then multiply each dimension by a learned
  weight. Keeps the scale under control as the stream grows. Cheaper than GPT-2's LayerNorm (no mean,
  no bias), and works as well.
- **RoPE:** attention by itself has no notion of order. RoPE treats the 64 dimensions of each query and
  key as 32 pairs and rotates each pair by an angle of `position × frequency`. Because rotating both
  vectors and taking the dot product only depends on the *difference* of the angles, the score depends
  on the distance between two tokens, not where they are. Fast-spinning pairs see "1 vs 2 tokens back",
  slow ones see "about 100 tokens back". Test: `test_rope_score_depends_only_on_distance`.
  We use the "half-split" pairing `(i, i+32)` that Hugging Face uses, so SmolLM weights load directly.
- **SwiGLU:** two up-projections side by side. `SiLU(gate)` (a smooth ReLU) multiplies `up`
  element-wise: the gate decides how much of each neuron's value gets through. The product is what
  we'll draw as a neuron firing.
- **Grouped-query attention (GQA):** several query heads share one key/value head. Saves memory for the
  KV cache (M3). Our model doesn't use it (6 and 6) but the fixture model does (4 query, 2 kv), so the
  Rust engine is tested on it before M7 needs it.

**Size:** 8 layers × (attention 590k + MLP 1.18M) + embeddings 1.57M = **15.7M parameters**.

**Code:** `train/src/glasswing_train/model.py`. Read it top to bottom: `RMSNorm`, `rope_cos_sin` /
`apply_rope`, `Attention`, `MLP`, `Block`, `Transformer.forward`. Shapes are in the comments.
Parameter names copy Hugging Face's Llama layout (`model.layers.0.self_attn.q_proj.weight`).
`forward(tokens, trace=dict)` records every intermediate tensor: that is the fixture format now and the
data the visualization will draw later.

## 4. safetensors

A file format for tensors: 8 bytes of header length, a JSON header (name → dtype, shape, byte offsets,
plus free-form `__metadata__`), then the raw bytes. Loading is a memory copy. PyTorch's default `.pt`
format is a pickle, and unpickling can run arbitrary code, which matters as soon as you load weights
you didn't make. Our config travels in `__metadata__`, so one file rebuilds the model.
**Code:** `export.py`.

## 5. Golden fixtures

How will we know the Rust engine is right? `fixtures.py` builds a tiny model (2 layers, dim 64, GQA)
with random weights, saves it, runs three prompts through it and saves **every traced tensor**
(78 tensors, 216k numbers, 2.3 MB). In M2 the Rust test loads the same files and compares stage by
stage, so a bug reports as "p1.layers.0.q differs", not "the output is wrong".

The random weights are deliberately large (norm weights between 0.5 and 1.5, unit-scale linear
outputs). With training-style init (std 0.02) everything would be near zero and a forgotten norm weight
could hide inside the tolerance.

**Tolerance:** CI on Linux differed from my Windows machine by 1.6e-5 on a few logits. Float addition
isn't associative: `(a + b) + c` can differ from `a + (b + c)` in the last bit, and different CPUs and
BLAS libraries sum the 64 terms of a dot product in different orders. So the parity bar is 1e-4,
relative and absolute. Rust will hit the same effect.

## Break-it lab: no causal mask

Prediction: loss drops much faster, because the model can read the answer; generation is garbage,
because at generation time the next token doesn't exist yet.

Small model (1.4M params), 400 steps, ~8 s on the GPU:

| | val loss at step 400 | sample after "Once upon a time" |
|---|---|---|
| with mask | 2.96 | "…there was a little girl named Mia. She loved to play with his toy cars. One day…" |
| **without mask** | **0.55** | "…knew did did but very both both did should did surprised both very very…" |

A loss that looks too good is a bug signal. Without the mask the model learned to *copy* the next token
instead of predicting it. In CI, `ruff` caught it first (the `future` variable became unused). That was
luck; three tests would have caught it anyway: the causality test, the causal-weights test and the
fixture test.
