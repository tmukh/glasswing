# M4 concepts: the engine in the browser

What M4 introduced, how each idea works, and where it lives in the code.

## 1. WebAssembly and wasm-bindgen

WebAssembly (wasm) is a compact bytecode every browser can compile to machine code and run in a
sandbox: no file system, no network, only the memory it's given. Rust compiles to it directly
(`--target wasm32-unknown-unknown`). The result is fast: our traced generation runs at **285 tokens/s
in V8 (Node, same engine as Chrome)**, about the same as native.

Wasm only knows numbers. **wasm-bindgen** generates the glue so JavaScript can call Rust with strings,
byte arrays and objects: `#[wasm_bindgen]` on a struct and its methods (`crates/wasm/src/lib.rs`)
produces `glasswing_wasm.js`, which loads the `.wasm` and wraps every call (copying a `Vec<f32>` into a
`Float32Array`, for instance). The browser API is deliberately thin: `Engine::new(weights, tokenizer)`,
`reset`, `encode_prompt`, `step(token)`, `sample`. All logic stays in `glasswing-engine`, where native
tests cover it.

To make that possible, `Session` stopped borrowing the model (M3 had `Session<'m>` holding `&Model`):
a struct handed to JavaScript can't contain a borrow, so `Engine` owns the model and the session side
by side, and every `run` takes the model as a parameter.

## 2. A Web Worker

JavaScript in a page runs on one thread, the same one that draws the page. A 200-token story is a
second of pure computation, which would freeze scrolling and animations. A **Web Worker** is a second
thread with its own event loop; the page and the worker only exchange messages. `web/worker.js` loads
the wasm and the weights, generates, and posts one message per token. Large arrays are
**transferred**, not copied: ownership of the buffer moves to the page in O(1).

Between tokens the worker yields (`await setTimeout 0`) so a "stop" message can get in.

## 3. f16 weights

| format | bits | exponent | mantissa | largest | precision |
|---|---|---|---|---|---|
| f32 | 32 | 8 | 23 | 3.4e38 | ~7 digits |
| f16 | 16 | 5 | 10 | 65504 | ~3 digits |

Trained weights are small numbers (our largest is 1.41), so f16's range is no problem; what's lost is
precision. Storing weights as f16 halves the download: **62.9 MB → 31.5 MB**. The engine widens them
back to f32 when loading (`safetensors.rs::f16_to_f32`: re-bias the exponent from 15 to 127, shift the
mantissa by 13, and handle zero, subnormals, infinity and NaN), so the math is unchanged.

Result: greedy stories from the f16 file are identical to f32 for all three test prompts. Speed is
unchanged too, because memory holds f32 either way; keeping f16 in memory (and converting in the dot
product) is the next step if the browser ever needs it.

## 4. SIMD in WebAssembly

Wasm has 128-bit SIMD (`simd128`): four f32 lanes, supported by every current browser. It's off by
default; `.cargo/config.toml` turns it on for the wasm target. The M3 `dot()` with eight independent
sums is what lets the compiler use it.

| wasm build | traced tokens/s (Node) |
|---|---|
| without simd128 | 193 |
| with simd128 | 285 |

## 5. Size budgets and the release bundle

The CI `web` job builds the bundle with a pinned, checksum-verified `wasm-bindgen`, fails if the wasm
grows past **400 KB** (it's 288 KB), and checks that **wasm and native generate the same greedy text**
on the fixture model. That catches bugs that only exist in the browser build, such as the SIMD path.

`release.yml`: pushing a `vX.Y.Z` tag builds the bundle in CI from the tagged source and attaches it to
a GitHub Release. The trained weights come from the training machine (`gh release upload`). The site
pins every file by sha256.
